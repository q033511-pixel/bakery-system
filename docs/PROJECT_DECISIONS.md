# القرارات الهندسية — PROJECT_DECISIONS.md

سجل الافتراضات والقرارات (بند 6/154): كل قرار قابل للتغيير لاحقاً وموثق بسببه.

## 1. المكدس: Vite + React بدلاً من أي بديل
مواصفة الزبون (بند 3) تفرض صراحة React + TypeScript + **Vite** + GitHub Pages. حُفظت كل متطلباتها حرفياً.

## 2. HashRouter للتنقل
GitHub Pages استضافة ثابتة بلا server rewrites (بند 3/167). HashRouter يضمن عمل refresh وdeep links دون إعداد خادم. حماية إضافية: `404.html` = نسخة index.html.

## 3. تمثيل JSON payload واحد لكل RPC بدل معاملات متعددة
`create_sale(p_payload jsonb)` — مرونة في التطور، تواقيع مستقرة، وسهولة إعادة إرسال نفس payload من طابور المزامنة (نفس البيانات تتخزن حرفياً في IndexedDB).

## 4. مصفوفة الصلاحيات مكررة في موضعين متزامنين
`role_has_perm()` في SQL (الفرض) + `ROLE_PERMISSIONS` في TS (الإظهار فقط). السبب: الفرض يجب أن يعمل بلا اعتماد على بيانات seed، والواجهة تحتاج فحصاً متزامناً محلياً. التوثيق في ARCHITECTURE.md يوجب تحديثهما معاً.

## 5. أول مالك برمز تهيئة (system_setup)
بدل "أول من يسجل يصبح مالكاً" (غير آمن — بند 68): المigrations تنشئ `system_setup` برمز عشوائي لا يُقرأ من العميل (بلا RLS policies)، ويستهلك bootstrap الرمز مرة واحدة. استخراج الرمز يتطلب صلاحية SQL — متاحة لمن أنشأ المشروع أصلاً.

## 6. مبيعات التوزيع بلا حركة SALE_OUT
البضاعة تخرج بالمحمولة `DISTRIBUTION_LOAD_OUT`. البيع أثناء الجولة = فاتورة مالية مرتبطة بالحمولة فقط. المرتجع يعيد المخزون. النتيجة: معادلة المحمول=مبيع+مرتجع+فرق مطابقة تماماً لحركات المخزون دون ازدواجية.

## 7. تسوية التوزيع تجمع الكميات بالوحدات الأساسية
مجاميع `loaded/sold/returned/unaccounted` في `distribution_settlements` بالوحدة الأساسية (لأن الأصناف تختلط: ربطة+كغ)، مع `product_breakdown jsonb` لتفصيل دقيق لكل صنف في الواجهة.

## 8. إلغاء الشراء لا يعيد حساب avg_cost التاريخي
`void_purchase` يعكس حركات المخزون والنقدية لكنه لا يعيد حساب المتوسط المرجح السابق (يتطلب إعادة حساب كامل السجل). أثره محدود ويوثق هنا — يمكن إضافة recompute job لاحقاً.

## 9. مبيعات التوزيع النقدية تُحصّل في الصندوق عند التسوية
حركة الصندوق الوحيدة لحملة التوزيع هي `cash_collected` في التسوية (لا حركة لكل تسليم نقدي) — يطابق الواقع: النقد مع الموزع حتى نهاية الجولة، والفرق النقدي يُدقق في التسوية.

## 10. الطبقة repositories دُمجت في services
مواصفة البنية (بند 7) تقترح repositories; لصالح البساطة وقابلية الاختبار دُمجت واجهات الوصول في `services/*` فوق Supabase — فصل الطبقات محفوظ (UI لا يلمس SQL إلا للقراءة البسيطة).

## 11. exactOptionalPropertyTypes معطلة في tsconfig
بقيت بقية أعلام strict مفعلة. السبب: الاحتكاك مع أنماط React/Supabase SDK المكتبية كان أثقل من قيمتها الإضافية في هذا المشروع. قرار قابل للإعادة لاحقاً بجولة تنظيف أنواع.

## 12. خدمة رصيد المخزون "تلميح" في شاشة البيع
`stockHint` يقرأ `v_stock` من الخادم للعرض التحذيري، لكن **القرار النهائي دائماً للخادم** عند الحفظ (بند 43). أوفلاين يظهر التلميح فارغاً — مقبول لأن الفحص الفعلي يحدث عند المزامنة/الحفظ.

## 13. عملة افتراضية ILS/₪ (بند 62)
حسب المواصفة، قابلة للتغيير من إعدادات النشاط، ورمز العملة لا يدخل منطق الأعمال أبداً (formatMoney يأخذ الرمز من الإعدادات).

## 14. العمل الجاري أوفلاين يحفظ "date المحلي"
الحقول التاريخية تُرسل من العميل (`sale_date` إلخ) بصيغة yyyy-MM-dd بتوقيت النظام — الخادم لا يستنتج "اليوم" من UTC في العمليات، و`business_today()` يُستخدم فقط كافتراضي وللترقيم ولوحة التحكم.
